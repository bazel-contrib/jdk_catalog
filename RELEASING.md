# Releasing

There are no published releases or BCR entries yet. Version `0.0.1` in
`MODULE.bazel` is the initial development version, not a published release.

## Versioning and support

Use Semantic Versioning for this module, independently of JDK version numbers.
Bug fixes and archive updates are patch releases; new JDKs or platforms are
minor releases. Removing a public toolchain label or raising the minimum Bazel
version is a breaking change (a minor bump before 1.0, a major bump afterwards).

When a JDK reaches the end of its vendor's maintenance window, document that it
no longer receives updates. Remove it only in an explicitly announced breaking
release. Existing module releases remain immutable for reproducible builds.

## Release checklist

1. Confirm the GitHub Actions matrix is green. Validate any newly added
   architectures on matching hosts or remote workers.
2. Update the module and consuming-example versions together. Record changes
   and supported JDK archives in the release notes.
3. Generate the API documentation as described in `docs/README.md`. Review
   the generated output and commit source changes before tagging.
4. Create and check out a `v<version>` tag. Prepare its archives:

   ```sh
   bash .github/workflows/release_prep.sh v0.0.1
   ```

5. Alternatively, run the **Prepare release** workflow with the existing tag.
   Like `rules_java`, this uses bazel-contrib's reusable release workflow and
   produces provenance attestations. It creates a draft release for review;
   publish it after checking the assets and notes. Source URLs
   must point at the uploaded release asset, not GitHub's autogenerated archive.
6. Follow the [BCR contribution guide](https://github.com/bazelbuild/bazel-central-registry/blob/main/docs/README.md)
   to prepare a registry submission. `.bcr/` contains metadata and source
   templates plus presubmit configuration. Fill in the archive integrity using
   the published asset and verify the consumer test module before submitting.
7. The **Publish to BCR** workflow follows `rules_java`'s `publish-to-bcr`
   convention. Set up a writable BCR fork and `BCR_PUBLISH_TOKEN` as documented
   by [publish-to-bcr](https://github.com/bazel-contrib/publish-to-bcr/tree/v1.1.0).
   Invoke it with the published tag and fork; it prepares a draft registry PR.
   Both workflows are manual until release and ownership arrangements are
   settled. Keep BCR CI green for each release.

If preparing the release locally, configure BCR publication without attestations
unless the release was built by the bazel-contrib reusable workflow. BCR's
attestation verification expects that workflow's provenance.

After a repository transfer, update the homepage and repository owner in
`.bcr/metadata.template.json`, README links, and CODEOWNERS as needed. Source
templates already use `{OWNER}` and `{REPO}` placeholders.

The repository owner publishes tags, releases, and registry submissions.
